# BytePulse

A fast, open source disk usage analyzer for Windows, built with WinUI 3 and .NET 10.

BytePulse reads a file system into a compact tree and shows what is using the space:
as a sortable grid, a ring chart, a treemap, a plain tree, or from the command line.
It is MIT licensed, has no telemetry, no advertising and no paid edition.

> **Status: early.** The engine, the command line tool and the main views work and
> are tested. Several features in the design are not built yet; see
> [Status](#status) for exactly what is and is not there.

## Why it exists

Disk usage tools tend to be proprietary, slow, or both. BytePulse is built around
three ideas:

- **Read directories with several threads at once.** A single threaded walk leaves
  most of the machine idle. For a tool that runs for a minute, that is the whole
  difference.
- **Keep the tree compact.** A node is an index into a few columns rather than an
  object graph, and names live in one shared blob, so a tree with millions of nodes
  fits in ordinary memory and one folder can be re-sorted without touching anything
  else.
- **Never hide what it could not read.** A tool that silently skips folders it was
  refused reports a total that is simply wrong. BytePulse says so instead.

## Speed

Measured on an i5-13450HX with .NET 10, warm file system cache. The baseline is a
single threaded recursive walk using the framework's own enumeration, which is what a
typical disk usage tool does.

A synthetic tree of 20 000 files, generated by `bytepulse-treegen`:

| Walk                                     | Mean       | Relative |
| ---------------------------------------- | ---------- | -------- |
| Naive framework walk, one thread         | 1 422.7 ms | baseline |
| BytePulse scanner, one thread            | 68.8 ms    | 0.05×    |
| BytePulse scanner, four threads          | 46.5 ms    | 0.03×    |
| BytePulse scanner, eight threads         | 31.4 ms    | 0.02×    |

That is roughly **45× faster than the naive walk**, with identical results at every
thread count.

On real trees:

| Tree | Contents | One thread | Four threads | Eight threads |
| --- | --- | --- | --- | --- |
| `C:\Windows` | 490 124 files, 152 859 folders | 28.6 s | 10.0 s | 8.8 s |
| `C:\` | 2 304 376 files, 408 596 folders | — | — | 62 s |

These numbers come from one machine. Run them yourself:

```powershell
dotnet run -c Release --project tests/BytePulse.Benchmarks
```

## Status

Working and tested:

- The engine: parallel directory walk, compact tree, subtree totals, per-folder sorting.
- The command line tool, with summary, tree, JSON and CSV output.
- The application: a virtualized tree grid with sortable columns, a ring chart of the
  largest folders, a treemap on the Map page, live progress, and cancellation.
- Size on disk (opt-in) and hard link detection (opt-in).
- Home, About and Settings pages, with settings saved between runs.
- Saying how many folders could not be read, and offering to restart with
  administrator rights.

Not built yet:

- Finding duplicate files by content hash.
- The privileged NTFS mode that would read the file table directly.
- Resizable columns, and a few smaller pieces of polish.
- A signed release.

BytePulse does not claim to be a finished replacement for anything yet.

## Requirements

- Windows 10 version 1809 (build 17763) or later, x64 or ARM64.
- To build: the .NET 10 SDK. Nothing else; the Windows App SDK comes from NuGet, and
  the engine and command line tool have no third-party dependencies at all.

## Building

```powershell
dotnet build BytePulse.slnx -c Release
dotnet test  BytePulse.slnx -c Release
```

The build treats warnings as errors, and the engine's tests cover the parser, the tree,
the aggregation, sorting, hard links, the walker, cancellation and the unreadable
folder reporting.

Run the application:

```powershell
dotnet run --project src/BytePulse.App
```

Run the command line tool:

```powershell
dotnet run --project src/BytePulse.Cli -- scan C:\ --top 20
```

## Releases

`scripts/publish.ps1` builds both things a release consists of.

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\publish.ps1
```

It writes to `artifacts/`:

- `BytePulse-<version>-win-x64.zip`, a self-contained folder that runs on a machine
  with no .NET and no installer, containing both the application and the command line
  tool.
- an MSIX package, unsigned unless a certificate is passed with `-CertificatePath`.

`-PortableOnly` skips the package, and `-Runtime win-arm64` builds for ARM.

The Windows App SDK runtime is included in the self-contained build, which is why the
zip is around 140 MB.

## Command line

```
bytepulse scan <path> [options]

  --json            write the results as JSON
  --csv             write the results as CSV
  --tree            write the whole tree, indented
  --threads <n>     how many threads read directories at once
  --sort <key>      name, size, files or modified
  --top <n>         how many entries the summary lists
  --follow-reparse  follow junctions and symbolic links
  --no-hidden       leave hidden and system files out
  --size-on-disk    read how much space each file occupies on disk
  --hardlinks       count a file with several hard links once
```

For example:

```powershell
bytepulse scan C:\ --top 20
bytepulse scan D:\ --json | jq '.roots[0].children | sort_by(-.totalBytes)[:5]'
```

Progress goes to standard error, so piping the results somewhere else stays clean.

## How it is put together

```
src/BytePulse.Core      the engine; no UI, no third-party packages
  Storage               chunked columns and the shared name blob
  Model                 the tree, sorting, and the flattened row model
  Native                the Win32 calls and the parser for what they return
  Scanning              the parallel walker, and the opt-in detail pass
  Hosting               whether the process is elevated
tools/BytePulse.TreeGen writes a synthetic tree for benchmarks
src/BytePulse.Cli       the command line front end
src/BytePulse.App       the WinUI 3 front end
tests/                  unit tests and benchmarks
```

The engine is `net10.0-windows10.0.17763.0`; the application is
`net10.0-windows10.0.26100.0`. The command line tool and the window use the same
engine, so a scan behaves the same in either.

### How a scan works

A worker takes a directory from a shared queue, reads its entries, adds them to the
tree, and queues the subdirectories it found. Node ids come from one atomic counter,
which guarantees a parent's id is always lower than its children's; that is what lets
subtree totals be accumulated later in a single pass over the nodes in reverse, with no
recursion. Each directory's children are linked by the single worker that read it, so
the hot path takes no locks.

The queue never blocks. A worker that finds it empty waits only while directories are
still queued or being read, so there is no state in which work exists that nobody can
reach.

A directory that cannot be read is recorded and the scan carries on. A cancelled scan
returns the part of the tree it managed to read.

### Sizes

"Sizes" means the logical size of the files. Directories report no size of their own
on NTFS, so a folder's total is the sum of the files beneath it.

### Folders that cannot be read

Some folders are refused even to ordinary users, and on a system volume that adds up to
a meaningful amount of space. BytePulse never hides this: a scan reports how many
folders it could not read and says that the total is lower than the real figure.

The application offers to restart itself with administrator rights, which reads most of
them. A few are reserved for the system itself, such as `System Volume Information`, and
stay refused even then; the scan says that instead of suggesting elevation would help.

Files such as `pagefile.sys` and `hiberfil.sys` are counted rather than skipped: they
occupy real space, and leaving them out would make the total wrong in the other
direction.

### Links and loops

Junctions and symbolic links are not followed by default, so a loop through one is
impossible. When following is enabled, the target of each link is identified by opening
it, and a link whose target has already been followed is skipped rather than followed
again. A file with several hard links is counted once; the other names are shown and
marked, but contribute nothing to the total. Both of these need the opt-in pass.
