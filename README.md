# BytePulse

A fast, open source disk usage analyzer for Windows, built with WinUI 3 and .NET 10.

BytePulse reads a file system into a compact tree and shows you what is using the
space, as a sortable grid, a tree, or from the command line. It is MIT licensed,
has no telemetry, no ads and no paid edition.

## Why it exists

Disk usage tools tend to be either proprietary, or slow, or both. BytePulse is
built around three ideas:

- **Read directories with several threads at once.** A single threaded walk leaves
  most of the machine idle; reading directories in parallel is where the speed-up
  comes from.
- **Keep the tree compact.** A node is an index into a few columns rather than an
  object graph, and names live in one shared blob, so a tree with millions of nodes
  fits in ordinary memory and a folder can be re-sorted without touching anything
  else.
- **Never block the interface.** A scan runs on background threads and reports
  progress while the window stays responsive.

## Measured speed

On a tree of 20 000 files, generated by `bytepulse-treegen`, on an i5-13450HX:

| Walk                                         | Mean        | Relative |
| -------------------------------------------- | ----------- | -------- |
| Naive: framework enumeration, one thread     | 1 422.7 ms  | baseline |
| BytePulse scanner, one thread                | 68.8 ms     | 0.05×    |
| BytePulse scanner, four threads              | 46.5 ms     | 0.03×    |
| BytePulse scanner, eight threads             | 31.4 ms     | 0.02×    |

That is about **45× faster than the naive walk**, and the result is identical at
every thread count. On a real tree, `C:\Windows` (490 124 files in 152 859
directories) scans in 28.6 s on one thread, 10.0 s on four and 8.8 s on eight.

These are numbers from one machine and a warm file system cache. Run the
benchmarks yourself: `dotnet run -c Release --project tests/BytePulse.Benchmarks`.

## Building

You need the .NET 10 SDK. Nothing else: the Windows App SDK comes from NuGet, and
the engine and command line tool have no third-party dependencies at all.

```powershell
dotnet build BytePulse.slnx -c Release
dotnet test  BytePulse.slnx -c Release
```

### The application

```powershell
dotnet run --project src/BytePulse.App
```

### Releases

`scripts/publish.ps1` builds both things a release consists of: the
self-contained folder, zipped, and the MSIX package.

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\publish.ps1
```

It writes to `artifacts/`. Pass `-PortableOnly` to skip the package, `-Runtime
win-arm64` for ARM, and `-CertificatePath` to sign the package.

To produce a self-contained folder by hand:

```powershell
dotnet publish src/BytePulse.App -c Release -r win-x64 `
  -p:WindowsPackageType=None -p:SelfContained=true -p:WindowsAppSDKSelfContained=true `
  -o publish/portable
```

To produce an MSIX package by hand:

```powershell
dotnet publish src/BytePulse.App -c Release -r win-x64 `
  -p:WindowsPackageType=MSIX -p:GenerateAppxPackageOnBuild=true
```

The package is written to `AppPackages`. Signing is off by default; set
`AppxPackageSigningEnabled` and point it at a certificate to sign a release.

## Command line

```
bytepulse scan <path> [options]

  --json            write the results as JSON
  --csv             write the results as CSV
  --tree            write the whole tree, indented
  --threads <n>     how many threads read directories at once
  --sort <key>      name, size, files or modified
  --top <n>         how many entries the summary lists
  --follow-reparse  follow junctions and symbolic links
  --no-hidden       leave hidden and system files out
  --size-on-disk    read how much space each file occupies on disk
  --hardlinks       count a file with several hard links once
  --version         print the version
```

For example:

```powershell
bytepulse scan C:\Users --top 20
bytepulse scan D:\ --json | jq '.roots[0].children | sort_by(-.totalBytes)[:5]'
```

## How it is put together

```
src/BytePulse.Core      the engine; no UI, no third-party packages
  Storage               chunked columns and the shared name blob
  Model                 the tree, sorting and the flattened row model
  Native                the Win32 calls, and the parser for what they return
  Scanning              the parallel walker
tools/BytePulse.TreeGen writes a synthetic tree for benchmarks
src/BytePulse.Cli       the command line front end
src/BytePulse.App       the WinUI 3 front end
tests/                  unit tests and benchmarks
```

The engine is `net10.0-windows10.0.17763.0`; the application is
`net10.0-windows10.0.26100.0`. The engine is the same code the command line tool
and the window both use, so a scan behaves the same in either.

### How a scan works

A worker thread opens a directory, reads its entries, adds them to the tree, and
queues the subdirectories it found. Node ids come from one atomic counter, which
guarantees a parent's id is always lower than its children's; that is what lets
subtree totals be accumulated later in a single pass over the nodes in reverse,
with no recursion. Each directory's children are linked by the single worker that
read it, so the hot path takes no locks.

A directory that cannot be read is recorded and the scan carries on. A cancelled
scan returns the part of the tree it managed to read.

### Sizes

"Sizes" means the logical size of the files. Directories report no size of their
own on NTFS, so a folder's total is the sum of the files beneath it.

### Links and loops

Reparse points, such as junctions and symbolic links, are not followed by default,
so a loop through one is impossible. When following is enabled, the target of each
link is identified by opening it, and a link whose target has already been followed
is skipped rather than followed again.

### Deployment

The application ships two ways from one project: a self-contained folder, which
needs no installer and no .NET runtime, and an MSIX package. The Windows App SDK
is included in the self-contained build.
